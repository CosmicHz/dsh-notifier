# dsh-notifier v1 完整重构实施计划

版本：1.1；日期：2026-10-05；状态：可作为实施主计划，尚未实施。

授权范围：编制完整计划。实施、提交和发布不是本次已完成事项。
基线：main@9d69dd7，package 0.13.1；实现前须对齐当时 dev 与现有重构分支，不能用旧 main 覆盖已完成重构。
需求优先级：用户当前“新设计不向后兼容、旧数据尽力导入、旧功能后续退役”及“完整高质量交付” > 本计划 > 旧 FINAL 包的执行指令。本计划替代旧包中的限时降标、删测试、Mock 生产服务和 TODO 交付策略。
本轮不要求真实设备、真实渠道账号或真实投递验证；其缺席不得被宣称为已验证，也不得用来降低代码、协议、集成与自动化质量。

## 1. 最终产品目标与范围

交付一个功能完整、可升级、可恢复、可维护的 DSH 通知与远程控制插件：28 个既有出站渠道、6 个既有入站控制渠道，统一账号、身份、路由、消息、控制与证据模型，完整 Native 管理界面。保留已定产品能力目标，不要求旧代码、旧接口或旧行为细节等价。

先确定完整目标再分阶段实施。阶段用于控制集成风险，不改变最终范围。没有“先发缩水版再补齐”的交付安排；内部里程碑仅用于验证，最终版本必须通过全部门槛。

### 1.1 固定范围

- 保留所有既有出站能力，包括群机器人/Webhook 通知；群聊出站不等于群聊控制。
- 6 条入站保持私聊控制，群聊远程控制默认拒绝；不按 group/channel/webhook 关键词删代码。
- 既有通知、对话、审批、路由等作为产品需求参考；v1 工具/API/命令按新合同设计，不要求旧名称、参数、返回值或后台端点继续可用。
- 新增/完善稳定 Account、账号范围内的身份绑定、引用回复完整链路、统一媒体接入、统一 Native 管理。
- v1 Native 是新版本日常管理 UI，CLI 提供新版本配置、状态和恢复。旧功能、旧 Console 与旧实现留在旧版本/独立 legacy 边界，后续另立退役任务；不要求 v1 逐端点替代旧 Console，不让旧功能清理阻塞 v1。
- 保留 Node >=22、ESM、零强制运行时依赖；现有可选 SDK 保持懒加载。开发/构建/浏览器测试依赖不等于生产运行时依赖。
- 不提供旧 notifier API、RPC、配置、事件载荷、exports 或内部接口兼容层；发布 v1 新合同及 breaking-change 说明，消费者按新合同升级。

### 1.2 不以“最好”扩张无关范围

本次不自动加入新 IM 平台、云同步、多租户服务或完整 Artifact 发布系统。引用和附件必须有来源范围校验，但不因此另造与宿主竞争的产物平台。权限以 v1 明确的账号/会话模型为准，不复制历史特例。

### 1.3 完成不可妥协项

1. 禁止关闭失败测试、空断言、删业务入口以获得通过。
2. 禁止内存 Mock 替代生产持久化；禁止生产 UI 接全成功假后端。
3. 禁止把 accepted、mock 或 contract-tested 标为 confirmed/真机完成。
4. v1 自身的数据正确性、权限、下载安全和核心恢复不可降标；旧数据导入允许部分成功或全部跳过，不是 v1 核心前置条件。
5. 功能故障可安全降级为明确 unavailable/desktop fallback；这属于运行时正确性，不是削减交付标准。
6. 任何用户可触发的操作都必须有真实后端、错误语义、状态回显和自动化验收。

## 3. 目标架构与确定的设计决策

### 3.1 依赖方向

DSH Host / Native RPC / CLI / Provider Transport
→ 已认证、标准化的事件或命令
→ Application Services（账号、配置、路由、通知、交互、会话控制）
→ Domain Contracts（身份、消息、状态机、权限与证据）
→ Store / Host ports / Provider adapters。

规则：UI 与适配器不直接写 Store；渠道不得自行实现另一套审批或权限决策；公开 API、RPC、CLI 共用应用服务；配置、运行时、UI 读取同一权威状态。
v1 按新合同组织模块，允许重写；旧代码仅作参考，只有清晰、独立、通过 v1 测试的实现才可择优复用。不得让 v1 核心 import legacy 运行时、读取旧 schema 或堆叠旧版分支。新存储目录、运行入口和 transport 所有权独立；同一平台账号的旧新消费者默认不能同时启用，避免争抢更新与重复投递。

### 3.2 Account、Destination、Identity 分离

- Account：平台连接/凭据主体。accountId 使用独立生成并持久化的 opaque ID，不使用 token 或整个配置哈希；token 轮换不改 ID。
- providerAccountId：可选的平台身份，经平台响应或配置规则确定，仅用于平台身份及重复账号识别。
- Destination：投递目标，以 destinationId 关联 Account，保留 chatId/userId/webhook 目标等渠道细节；同一 bot 发多个目的地不必复制逻辑账号。
- Principal/Binding：以 (channel, accountId, userId) 唯一标识权限绑定，独立保存 role、label、配对来源、时间和作用域；全局相同 userId 不共享权限。
- Channel 类型由 v1 canonical registry 定义；旧别名仅可在独立导入器转换，核心不接受历史别名。
- 修改 Account 不隐式删除 Identity；删除账号原子撤销关联授权、停 transport、使待办与引用失效；审计保留脱敏 tombstone，不残留可用授权。
- 可选导入中账号关系存在歧义则跳过并报告；不猜测授权归属，不把歧义带入新模型。

### 3.3 revision、policyRevision、runtimeEpoch

- revision：账号/配置等资源更新的 CAS 版本，禁止客户端改写。
- policyRevision：身份授权、撤销、私聊开关和作用域变化时推进；执行控制操作时重新检查。
- runtimeEpoch：账号运行实例的代际标识，启动/替换/删除重建改变；迟到网络响应和旧回调不得写入新实例。
- 幂等操作使用 requestId/eventId；重复请求返回已处理结果，不重复发送不可安全重试的副作用。
- 日常显示名修改不得意外撤权；凭据身份变化则按明确规则重新鉴权和使旧执行资格失效。

### 3.4 共享状态与事务

按 v1 不变量设计 Store，可重写或择优复用实现；不保留旧方法签名。必须提供锁/并发控制、隔离快照、原子提交和失败关闭，并用新测试证明。
- 单次事务包含配对核销、Binding 创建、锁出清理；不能三次写盘。
- 资源 CAS 检查与写入位于同一事务；持久化失败不能返回成功。
- schemaVersion 与命名空间只有一个定义源；Registry、迁移器、诊断和测试读取同一 schema。
- v1 使用独立状态目录和 schema，禁止与旧版共写文件；无需兼容旧文件锁。
- 新运行时仅接受 v1 schema；旧未知字段留在原始备份，不导入新状态。v1 缓存、去重、审计、引用、游标均有上限、TTL/回收和损坏处理。
- 新快照必须隔离引用；读取结果不能意外修改内存中的权威状态。

### 3.5 配置与密钥

输入使用字段白名单和渠道 schema；嵌套 patch 明确定义 merge，不能整体浅覆盖。
敏感字段采用 keep/set/clear 语义；掩码占位符不是有效密钥；查询只返回 masked value/hasSecret，写入后清空客户端明文。
环境变量引用保留为引用，不在迁移时把解析结果永久写盘。v1 明确自己的配置来源及优先级，不必支持所有历史加载方式。
备份/状态文件权限至少保持现有 0600 best effort；日志、错误、活动、诊断不回显 token、完整 URL 密钥或私聊内容。

### 3.6 控制与副作用

新建统一 Control Core 与 Session Arbiter；stop > 当前 question > 当前 approval > steer > 普通消息，作为 v1 合同验证，不依赖旧控制实现。
交互必须携带来源账号/用户/聊天、会话/轮次、策略版本、到期时间；第一条有效回答胜出，其余返回 already_handled。
状态明确 pending、执行占用/claim、终态及过期/撤销/恢复分支；失败不默认批准。
持久化与外部执行不是天然原子：先记录执行意图/幂等键，执行后持久化结果；Host 不支持幂等确认时，崩溃后将不确定操作标为需核对，禁止盲目重放，也不承诺跨系统 exactly-once。

### 3.7 统一消息、引用与附件

Envelope 包含 channel/accountId/userId/chatId/chatType/messageId、接收时间、文本、附件及可选 replyTo；信任字段由认证后的适配器填充，不信任任意 payload 自报来源。
引用链：提取引用 → 有界缓存或渠道 resolver → 范围/权限检查 → 标准化 → Host prompt 内容。支持异步 resolver、AbortSignal 与总超时；无需远程查询的渠道直接返回。
引用缓存按账号/聊天/消息隔离，限制数量/大小/TTL；引用不可用给出明确原因，不伪造内容，不让上下文引用隐式切换会话或扩大权限。
附件链：来源验证 → URL/网络策略 → 有界下载 → Host AttachmentStore → 会话附件引用。无 saveFile 能力时返回明确 unsupported，不把远端 URL 当作已入库文件。
HTTP(S)、完整 IPv4/IPv6/映射地址校验、DNS 结果检查和连接固定、拒绝重定向、总超时/取消、实际读取字节上限、并发与文件名净化全部保留；压缩后的实际读入量同样受限。

### 3.8 渠道合同

区分 transport、rendering、capability；简单 HTTP 渠道继续声明式 spec，多步骤渠道用代码 adapter。
统一 validate/resolve/send、start/stop/dispose、health、可选引用/媒体/卡片能力；不要强迫所有渠道实现不支持的方法。
平台接受请求只记 accepted；显式投递回执才记 confirmed。测试回执作为 fixture 验证解析，不能变成生产投递记录。
统一状态 unconfigured/disabled/connecting/ready/degraded/restart-pending；配置已保存和连接已生效分开显示。

### 3.9 Native 与目标宿主

沿用宿主 React、slots、locale、Connection RPC；禁止无依据的 window.native。
G0 核实可用宿主版本，选择一个明确的目标版本/能力合同（以现有 0.1.7-rc.2 证据为候选，不无条件沿用整个历史矩阵）。只为目标宿主实现必要的安全接入；如其公开接口确有缺陷，可采用经过验证的最小接入方式并保留 Connection admission，不维护历史宿主 fallback 分支。
与当前目标宿主的真实集成是必需项；与旧 notifier/历史宿主的向后兼容不是目标。通过已发布包和本地 Host fixture 验证，不声称真机认证。
所有后台响应采用统一错误码、字段校验、鉴权、取消与体积限制；UI/CLI 不能绕过权限合同。

## 5. 新数据基础与可选旧数据导入

### P1：新模型和持久化先行

按 v1 模型建立独立 Store、Account、Destination、Principal/Binding、策略版本及状态目录。默认从全新配置开始，直接提供完整首次设置、登录和配对流程。P1 不要求任何旧数据转换成功。

G1：新安装、CRUD/CAS、原子配对、密钥 patch、损坏/写盘失败、并发、重启和 v1 自身备份恢复全部通过；新核心无 legacy 运行时依赖。通过后直接推进 P2。

### I1：独立、非阻塞的 best-effort 导入

在新模型稳定后开展，不位于 P1→P2 的关键路径；无需覆盖全部旧版本和状态格式。

- 仅支持容易识别且能可靠映射的账号配置、目的地、凭据/环境引用和简单偏好；路由仅在关联明确时导入。
- 身份默认重新配对；只有明确可证明账号、用户、作用域归属的记录才可导入，不复制旧 token、待办、执行资格、缓存、锁或游标。
- 未知版本、损坏数据、模糊身份、无法映射字段直接跳过，记录 imported/skipped/failed 和原因；允许零项导入，但只能显示“未导入，开始新配置”，不能报“完整迁移成功”。
- 读取一致、受保护的旧数据副本；无法取得可靠副本时跳过整个导入。旧目录只读，不原地升级，不删除原文件，也不要求新系统持有旧格式。
- 先 dry-run，再按 v1 schema 校验可用条目，通过新应用服务提交；导入错误不能污染已有新状态。重复导入幂等，冲突默认保留新数据并报告。
- 不为导入增加核心兼容层，不保留未知键在新 schema，不开发双向同步、历史数据修复或旧新版双写。
- 旧版和旧数据继续独立留存。切回旧版只涉及停止新账号 transport、启用旧实例，不提供 v1→v0 数据反向转换，也不承诺新数据可在旧版读取。

验收：实现了哪些转换就测试哪些转换；还必须测试未知/损坏/全跳过、原文件不变、重复导入、关联冲突、提交失败及全新配置继续可用。不设迁移成功比例，不把特定旧数据迁移成功作为 v1 发布条件。v1 自身的数据耐久性与恢复仍是强制门槛。

## 6. 运行时、控制与渠道实施

### P2：统一应用服务与运行时生命周期

涉及：src/assembly、runtime、control、interaction、approval、questions、routing、event-listener、tool-register、public。
- Account 保存走 canonical config，热应用结果有 desired/applied revision；失败状态可诊断。
- 所有 transport 有幂等 start/stop/dispose、启动截止时间、重连退避、取消与 epoch fence。
- 统一权限检查、命令仲裁、待办结算、去重及审计；UI、IM 和 CLI 共用入口。
- 保留事件监听、通知规则、路由、静默、notify 工具及外部插件服务。
- 针对持久化失败和 Host 调用不确定结果实现恢复语义，不把 try/catch 吞错当容错完成。
G2：用真实 Store、应用服务、RPC handler 和可控 Host 端口跑完 F03-F10/F13，重启前后状态一致；无生产 Mock。

### P3：渠道标准化与语义全链路

涉及：src/adapters、channels、inbound、security/network-policy、delivery-evidence、test/fixtures、渠道矩阵生成器。

- 长连接用本地 HTTP/WS/长轮询模拟器测试 auth、ACK、心跳、断线、恢复、游标和旧事件。

## 8. 非真机验证体系

### P5：回归、故障注入、性能和发行验证

外部账号和真机不作为本轮 gate。网络、Host 和时间可替换，业务核心、持久化和权限检查不能整体替换。

|层级|具体测试|成功标准|
|---|---|---|
|单元/性质|schema、CAS、权限、URL/IP、分段、回执、状态机|边界值、随机/生成输入、非法状态与错误路径有断言|
|真实持久化|临时文件、多实例/子进程竞争、崩溃/权限/空间错误|无丢键、无半迁移、无重复核销、失败不报成功|
|协议模拟|本地 HTTP/WS/轮询、记录 fixture|握手/鉴权/ACK/限流/重连/畸形输入/取消符合合同|
|Host 集成|实际插件装配+公开 Host 接口 fixture/可运行本地包|工具注册、事件、会话、问题、附件、RPC、dispose 完整|
|浏览器 E2E|真实客户端产物+真实本地服务|五页与所有关键用户旅程通过，响应式/双语/主题/键盘完整|
|数据恢复/可选导入|v1 恢复、受支持旧格式 fixture、失败注入|导入可跳过，原数据不变；新数据原子性、恢复与权限正确|
|打包兼容|npm tarball 安装到隔离目录|exports/类型/入口/客户端/patch/可选 SDK 缺失路径正确|

### 8.1 测试与覆盖率规则

- 每次行为变更：针对性测试→对抗审查→修正→全量回归；失败必须处理，不标 TODO 跳过。
- v1 测试围绕新合同独立建立。旧实现/兼容测试不要求通过或逐条移植；值得保留的安全、协议和业务案例择优转化。禁止为掩盖 v1 缺陷删除其有效测试。
- 新增/实质改动核心代码目标：行/语句 >=95%，分支 >=90%；安全、授权、事务、结算、迁移的不变量必须有完整正反例和故障注入，与百分比同时满足。
- v1 覆盖率单独计算，不与旧仓库比例比较；legacy 不进入 v1 测试和覆盖分母。工具与排除列表固定，除 legacy、生成物、纯类型和有理由的平台不可达代码外，不排除困难的新业务路径。
- 无空测试、无因失败增加 skip；平台条件跳过必须由 OS/capability 条件决定并在对应 CI 平台补测。
- 为 v1 提供完整 test/release-check/channel-matrix/target-host-check、语法与 npm pack 检查；可复用有效脚本，但命令名/实现不强制兼容旧版。测试发现与 CI 明确指向 v1，legacy 维护另行处理。

### 8.2 必测用户旅程

J01 空安装→添加账号/目的地→保存→测试→看到真实 accepted/失败。
J02 全新配置→重启→v1 备份恢复；另测可选导入部分成功/全跳过→报告→重新配置，不阻断使用。
J03 开启入站→配对→手机消息的模拟入站→Host 对话→出站回答。
J04 审批/问题到达→Native 与 IM 同时操作→仅一条有效结算→另一端显示已处理。
J05 忙碌中普通消息与 steer/stop→正确仲裁→任务/会话切换不串线。
J06 修改/清除密钥与禁用账号→权限和连接立即按合同变化→旧回调拒绝。
J07 引用+附件→安全准入→Host 接收→危险 URL/过大文件/无能力明确失败。
J08 网络断开→stale→重连→状态一致，重复事件不重复执行。
J09 磁盘失败/损坏→明确 degraded→不丢旧状态/不放宽权限→恢复。
J10 多账号同一 userId、多个 chat/session→路由正确且严格隔离。
J11 无可选 SDK、无 Native/headless→核心通知仍可用，CLI 可诊断和恢复。
J12 窄屏/中英/深浅/键盘→所有管理操作可达；大量待办可分页处理。

### 8.3 性能与长运行目标

G0 固定测量环境（OS/CPU/Node、样本、冷暖启动和统计口径），不在慢机器上用空实现换指标。
目标负载：28 出站配置、6 入站连接模拟、100 逻辑账号、1000 个绑定、100 待办、10000 条受限活动记录。该负载是工程验收样本，不是未经验证的产品上限。
- UI 交互反馈 p95 <=100ms，缓存 Tab 切换 p95 <=200ms；Host 依赖已就绪后控制面首次可用 p95 <=500ms，网络/Provider 延时单独呈现。
- 本地读 RPC p95 <=100ms、持久化配置操作 p95 <=200ms（排除外部 API）；安全与耐久性优先于指标。
- 有界列表不全量传回活动历史；分页/游标和响应大小受限。
- CI 快速生命周期压力循环 100 次；发布前本地合成 transport soak 至少 2 小时，包含丢包/重连/慢响应/突发事件。
- dispose 后账号所属 timer/listener/socket 为零；有界表不突破上限；预热后进程内存不得随每轮操作持续线性增长。保留曲线和诊断，不只报“没崩”。
- 未达标要定位和修复；调整验收环境或指标须记录设计依据，不能悄悄降标。

G5：所有功能旅程、合同和发布检查通过；无未关闭的阻断性数据/安全/核心功能问题；完整性能及故障注入记录可复查。

## 10. 工作拆分、依赖与风险

依赖：P0 → P1 → P2 → P3 → P5 → P6；I1 在 G1 后独立实施，不阻塞 P2/P3/P4，验收只检查导入安全和报告正确、不要求旧数据导入成功；P4 可在 G1 的数据/RPC 合同稳定后与 P2/P3 交错推进，但必须接真实服务完成 G4；G5 依赖 G3 与 G4。本文不要求多 Agent，单执行者按依赖推进即可。

每个任务记录：需求 ID、影响文件、前置合同、正反例、故障路径、迁移/兼容影响、验证命令、审查发现、提交。一个逻辑关注点一个提交，不混无关重排。

主要风险与处理：
- 已有重构与 main 分歧：先盘点已做工作，按合同复用，不重新从零。
- 模型变化牵动权限：v1 身份与事务先落地；旧授权默认不继承，不等待旧状态迁移。
- 外部副作用无法原子提交：幂等/执行日志/不确定结果核对，不盲重试。
- 目标 Host 接口差异：核实一个明确目标合同并验证，不维护历史版本矩阵。
- 私聊与群出站混淆：独立 capability 和明确矩阵，禁止关键词删除。
- legacy 拖累：旧版隔离留存、后续退役；v1 提供自己的恢复入口，不调用旧 Console。
- 计划膨胀：以 F01-F17 及已批准语义为范围，新增功能单独记录，不影响本轮完整交付。

不设 8/10 小时强制交付。排期在 G0 的真实规模和基线基础上估算；遇复杂问题改变实现顺序或工期，不改变数据、安全和完整性门槛。

## 11. 给实施者的执行指令

## 12. v1.1 修订决议

本轮按用户纠正：产品能力完整不等于向后兼容。旧实现不阻塞新架构，旧功能后续退役。v1 以独立新模型、新接口、新测试和目标宿主实现；只择优复用旧代码。旧数据能可靠导入就导入，否则跳过并重新配置；不扩张为历史修复工程，不要求无损迁移或反向降级。原数据隔离留存与新数据正确性依然成立。
